# Decisions (made autonomously — each says what, why, and how to change it)

1. **Fleetbase runs unmodified from its official prebuilt Docker images** (`docker/fleetbase/docker-compose.yml`, compose project `tadfb`). Why: spec says never fork its core. The console image has no arm64 build, so it runs as `linux/amd64` (static nginx; fine under emulation). Change: edit the compose file / `scripts/fleetbase-up.sh`.
2. **Our code is Node 22+/24 with the built-in `node:sqlite` and `node:test`** — no native modules, no extra DB server. One SQLite file (`.data/tad.sqlite`) holds our own tables (orders mirror, batches, driver_shifts, address book, audit log). Why: zero install, nothing to compile, easy backups. Change: `lib/db.js`.
3. **One process, many services.** Every service is a module with its own factory (`services/*.js`) wired together in `lib/context.js` and mounted on one Express server (`server.js`). Each can be pulled out into its own process later because they only talk through `ctx`.
4. **Our own order state machine lives in SQLite; Fleetbase gets the order at ingest and the driver assignment + dispatch at batch time.** Fleetbase has no "Ready" status, and the owner wants Accept/Ready on the board. Fleetbase stays the system of record for drivers, live map, proof of delivery and tracking numbers.
5. **Places are created first, then referenced by id** when creating Fleetbase orders (nested pickup/dropoff objects lose their address fields in the current Fleetbase API — verified live).
6. **Order type `transport`** is used for deliveries (Fleetbase's default config); collection (pick-up) orders never reach Fleetbase.
7. **VROOM is our own instance** (vroom-express); if it is unreachable the batcher falls back to a local nearest-neighbour sequencer and flags the run, so the shop never stops.
8. **Driver authentication to our platform** is a per-driver bearer token (issued by the admin, stored as a SHA-256 hash). Fleetbase keeps its own driver login for the Navigator app.
9. **Docker clean-up is scoped to our own compose project** (`docker compose -p tadfb down -v`, `docker image prune -f` for dangling layers only). The spec's `docker volume prune -f` is NOT used because it would delete the owner's other, unrelated Docker volumes (WordPress, MariaDB, etc.) that exist on this MacBook.
10. **Tests use only in-memory SQLite and in-process fakes** (no temp directories at all); the sweeper still runs at the start and end of `npm test`.
11. **Greater London OSRM graph locally, all-GB in production.** The laptop has ~3.8 GB for Docker; extracting GB needs ~16 GB RAM. `scripts/geo-osrm-prepare.sh` takes `PBF_URL`. Same code, bigger file. Change: set `PBF_URL=https://download.geofabrik.de/europe/united-kingdom-latest.osm.pbf` on the server.
12. **Photon pinned to 0.7.4 with the GB-only extract `photon-db-gb-250720`** (3.5 GB download, archive deleted after extracting). The newer Photon 1.x has no ready GB extract on graphhopper's server, only the planet (95 GB). Change: `PHOTON_VERSION` / `INDEX_URL` in `scripts/geo-photon-prepare.sh` when a 1.x GB extract exists. OS Places (paid key) is used first when `OS_PLACES_API_KEY` is set.
13. **Customer tracking polls instead of subscribing to Fleetbase's SocketCluster.** The page asks our server every 5 s while the order is out; the server asks Fleetbase for the driver's position at most once per 3 s per driver, so any number of customers cost Fleetbase one call per driver. Why: a socket client per customer page would need socket tokens and CORS holes; polling is simpler and proved fine at a single shop's volume. Change: `services/tracking.js` (`driverPoint`) is the single place to swap in a socket subscription.
14. **Fleetbase changes made in the Navigator app / console are picked up by `services/fbsync.js`** (every tick + optional webhook `/api/fleetbase/webhook?k=…`). When an order leaves a driver (requeue, cancel, unassign) its Fleetbase order is cancelled and detached, and a fresh one is created on the next assignment, so a stale "started" status can never move a later run.
15. **Reports and order numbers use shop time** (`timezone` setting, default Europe/London), not UTC.
16. **Push subscriptions are only accepted from real browser push services** (Google/Mozilla/Microsoft/Apple hosts), max 5 per order, to stop the server being pointed at arbitrary hosts.
17. **HubRise events are marked "seen" only after the order exists**; a failed one is kept in `ingest_failures` and shown on the board with Retry/Dismiss, so a paid order is never silently lost. The HubRise OAuth callback is protected by a one-time `state` instead of the login cookie (the cookie is SameSite=Strict and is not sent on the redirect back from HubRise).
18. **A run still being collected at the shop takes new nearby orders** (up to `max_tasks`, within `cluster_merge_km`) instead of making the order wait for another driver; the driver is told to scan the extra bag.
19. **Navigator web build is not used for verification.** The upstream web target (`yarn web`) already fails to compile on the untouched upstream commit (171 webpack errors), so the driver app is verified by its jest suite + typecheck only; an APK needs the owner's Android SDK / signing key.
20. **GPS trails are saved two ways at once**: the driver app posts positions to `POST /driver/location` (queued points are accepted in batches), and the server samples Fleetbase's driver locations on every tick. Both go through one throttle (one point per driver per 5 s; a stationary driver one per minute) into `driver_locations`, tagged with the run the driver was on. Why: the Navigator's own tracking only talks to Fleetbase, and a phone with no signal must not leave a hole. Retention is the `trail_retention_days` setting (default 90, 0 = keep for ever); old points are purged at most once an hour. Change: `services/trails.js`.
21. **Custom order fields are required only on the admin's Add order form.** Orders from the website, HubRise and the delivery platforms cannot always answer them, and an order that is already paid must not be refused for a missing "gate code". Field keys are generated once from the label and never change when the label is edited, so saved answers survive a rename; deleting a field hides its answers. Change: `lib/customfields.js` (`enforceRequired`).
22. **Blocking rules.** A blocked phone or address refuses a new order from our own website (HTTP 409 `customer_blocked`) and from Add order (the admin may tick "Add anyway", which is written to the audit log and the order timeline). Orders that arrive already paid from HubRise / Uber Eats / Deliveroo / Just Eat are **taken anyway** (refusing a paid order is worse) but shown in red on the board with the reason and logged. A merely flagged customer only warns. Address matching is postcode + the letters and digits of line 1, so "5 Bad Lane," and "5 bad lane" match. A privacy erase also clears the person's phone flags. Change: `services/flags.js`, `orders.checkFlags`.
23. **Incidents are our own table, not Fleetbase Issues**, so they sit in the same audit log and order timeline as everything else and can be exported as one CSV. Drivers can only report against their own orders (or about themselves); photos are stored like the failed-delivery photos. Fleetbase's native Issues screen in the driver app is untouched.
